---
title: Tickets
description: A ticket is a unit of work describing an intended outcome. This page covers references, statuses, subtickets, tags and trash.
---

A **ticket** describes an outcome you intend to reach. It has a title, a Markdown
description, a status and optional links to a project, a Plan, other tickets and
Documents.

## References

Every ticket has a short reference that is unique in the workspace, such as
`T-RL12`. The two uppercase letters identify the device that issued the reference. Use the value returned when creating your ticket. The reference stays with the ticket when it moves to another
project or Plan. Use it wherever a command asks for a ticket:

```sh
ticketd show T-RL12
```

## Status

| Status      | Meaning                                           |
| ----------- | ------------------------------------------------- |
| Todo        | Not started.                                      |
| In progress | Being worked on.                                  |
| In review   | Implementation is finished and review is pending. |
| Done        | Complete, with no further review required.        |
| Canceled    | The work will not continue.                       |
| Duplicate   | Describes the same outcome as another ticket.     |

```sh
ticketd change T-RL12 --status "In review" --agent coding-agent
```

Changing one ticket's status never changes another ticket's status.

## Parent tickets and subtickets

A ticket can be broken into subtickets. A parent ticket still has its own
outcome: it can be Done while subtickets remain open, and finishing every
subticket does not finish the parent. A subticket can belong to a different
project or Plan than its parent.

```sh
ticketd set-parent T-RL14 --parent T-RL12
```

Omit `--parent` to remove the parent.

## Tags

Tags come from one vocabulary shared across the workspace. They are trimmed and
lowercased, and adding a tag twice has no effect.

```sh
ticketd add-tag T-RL12 security
ticketd list --tag security
```

## Projects

A **project** is a repository that tickets can be linked to. When you create a
ticket from inside a registered checkout, ticketd links it to that project. See
[Connect an agent](/docs/agents/connect#project-context).

## Duplicates

When two tickets describe the same outcome, the canonical ticket carries the work. The duplicate keeps its own reference and history.

```sh
ticketd preview-duplicate T-RL15 T-RL12
```

If the preview lists no blocking dependencies, run `ticketd mark-duplicate T-RL15 T-RL12`. When it lists dependencies, review each one. You can move the edge to the canonical ticket, remove it, or keep it on the duplicate. Apply those decisions together in the desktop app or through a [reviewed CLI request](https://github.com/vantoan19/ticketd/blob/main/docs/cli.md#duplicates). A retained Duplicate blocker keeps its dependent waiting.

## Trash

Trashing removes a ticket from ordinary lists and from work selection. Nothing is
deleted permanently: a trashed ticket keeps its relationships and can be restored.

```sh
ticketd trash T-RL15
ticketd trash-list
ticketd restore T-RL15
```

A trashed ticket must be restored before it can be edited.
