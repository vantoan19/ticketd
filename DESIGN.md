# ticketd interface design

## Purpose and authority

This document defines the target visual and interaction design for ticketd's desktop application and the design system it is built from (section 11). It is a specification for design work and review; the current interface is not evidence that these rules have been implemented. Dimensions are logical CSS pixels at 100% zoom. Minimum heights must grow for wrapped text and accessibility settings.

Use [GLOSSARY.md](GLOSSARY.md) for domain language, [the product description](docs/product.md) for behavior, and [the architecture](docs/architecture.md) for technical boundaries. This guide defines how those behaviors are presented. The experimental native Chat screens ([product description](docs/product.md#native-chats)) are off by default and follow this guide’s tokens and components; their layout is specified in section 15. For tickets owned by an external source, starting with GitHub Issues ([#98](https://github.com/vantoan19/ticketd/issues/98)), it defines how ownership, freshness, and source content are presented; that issue defines the synchronization behavior. Report design bugs and proposed improvements in GitHub Issues. Organize implementation steps locally in ticketd.

### Reference and adaptation

The visual reference is the third-party [Vercel design language analysis by design-bites](https://github.com/educlopez/design-bites/blob/main/design-mds/vercel.com/DESIGN.md). Use its published numeric values for the light palette, type scale, control sizes, spacing scale, radii, focus treatment, and elevation. It is a third-party observation rather than an official Vercel specification. The tables below distinguish those source values from ticketd-specific layout assignments and dark-theme extensions.

Use a Linear-style issue workspace with the Vercel palette and components. Ticketd needs its own application composition: a persistent workspace, a scan-friendly ticket list, a readable document, and reliable editing feedback. Map the reference roles onto these application surfaces without inventing replacement token values. Ticketd uses an explicit compact application heading of 24px/32px with weight 600 and -0.6px tracking. This is a ticketd density adaptation, not a value copied from the reference. The 32/40 display role is reserved for expanded titles and first run. Workspace pane widths and responsive transitions are ticketd layout decisions. Vercel branding does not belong in this workspace. Use the reference’s shadow boundaries and spacing-led grouping.

The workspace structure also borrows interaction patterns that Linear, GitHub Issues, and Orca share: a ticket list grouped by status, a wrapping property bar above the document, an external issue’s description shown as a read-only source card, and its comments and events on one connected timeline. Borrow these structures, not those products’ styling or branding.

## 1. Visual character and hierarchy

The interface should feel composed, legible, and predictable. A person should identify the current view, selected ticket, status, and next action without inspecting a collection of equally prominent controls.

Use three levels of emphasis:

1. **Work content:** ticket titles, descriptions, updates, and meaningful results. These have the strongest text contrast and the largest share of the screen.
2. **Context:** status, project, Plan, relationships, and evidence. These stay readable and close to the content they describe.
3. **Operations:** follow, reminder configuration, filters, editing controls, and administrative actions. These have compact triggers and reveal their forms when requested.

Visual simplicity must not erase useful information. Existing prerequisites, duplicate links, evidence, and scheduled reminders need visible summaries. Hiding everything behind accordions is not an acceptable substitute for hierarchy.

### Composition rules

- Establish grouping with alignment and spacing first. Use a shadow boundary where navigation or independently scrolling planes meet. Separate document sections with spacing.
- Use flat document sections. Do not wrap each property, empty state, or relationship type in its own card. Use cards sparingly: the read-only description from an external source is the one card on a ticket. Comments, updates and evidence are rows on the page, not cards (see Documents and activity).
- Give each action surface one primary action. The workspace's New ticket action and a focused dialog's submit action may coexist.
- Keep headings, body text, inputs, and section actions on consistent left and right edges.
- Keep small supporting text readable. Do not use low contrast, tiny text, or excessive truncation to make a screen seem cleaner.
- Avoid repeated toolbars, duplicate headings, decorative gradients, large status fills, and animations that move the work under the pointer.

`--muted` and `--secondary` are shadcn aliases of `--recessed` and `--secondary-foreground` of `--muted-foreground`; new code uses the semantic names. `--popover` is `--surface` in light and one step above it in dark, so menus, popovers, selects and command lists never share the panel's fill; dialogs and sheets stay on `--surface` over their scrim. Use `#4D4D4D` for necessary small text, including timestamps. The reference’s `#8F8F8F` is not a readable-body-text substitute; disabled labels use `#6B6B6B` (5.3:1 on white) because they stay readable without opacity dimming. Tooltips are one small dark chip in both themes. If shared components use `muted-foreground` for captions, map it to the secondary text role and keep the decorative/disabled role separate.

Primary actions invert the existing primary/elevated pair: `#171717` fill and `#FFFFFF` text. Ghost actions begin transparent with secondary text and promote to primary text on `#EBEBEB` hover. Standard prose links may retain primary text with an underline, as in the reference’s standard-link treatment; use the blue token for focus and link decoration. Never reduce contrast merely to make all links blue. Source links use the accessible text-link role `--link-foreground`: `#005FCC` in light and `#52AEFF` in dark; focus and decorative interactive accents keep their existing tokens. Recessed notices and footer bands retain a shadow boundary when their fill alone is too close to the surrounding surface.

The reference also supplies indicator colors: blue `#0062D1`, cyan `#52AEFF`, teal `#45DEC5` / `#067A6E`, green `#398E4A` / `#45A557` / `#6CDA75`, orange `#FF990A`, red `#E5484D`, pink `#EA3E83`, and purple `#7820BC` / `#BF89EC`. Reserve these for small indicators, approximately 10px, when the meaning requires color. Do not introduce colored status panels. Ticketd keeps status icons neutral; status color appears only as a small dot beside a word (see Status and state vocabulary), never as a fill, panel, or icon tint.

The Automation canvas is the one exception, because a flow is read by the kind of each step and a run by where each step stands. There a card's 28px icon tile takes a color: in the editor the trigger is blue (`--interactive`), Run agent is solid (`--foreground`), If is violet, Change ticket teal and Notify me pink; in a run the tile takes the step's status color instead, and Taken over is violet. The three added tokens use the reference indicators: `--violet` `#7820BC` light and `#BF89EC` dark, `--teal` `#067A6E` and `#45DEC5`, `--pink` `#EA3E83` in both. Every tile still sits beside the step's kind and its status in words.

### Status and state vocabulary

Use the shared `StatusIcon` plus text at 16px (rows and headers), 14px (cards and chips), or 12px (minimum). Its custom SVG family uses a 16-unit grid, neutral tokens and fill to show progress; the status registry also supplies history. Named glyphs announce the status; beside a visible status word they are decorative. Where color adds meaning (Ready, Blocked, unread, checked), use a small status dot (about 10px or less) placed beside a word. A dot never appears alone, and it is the only place status color is used.

| Meaning            | Icon treatment                                          | Visible label       |
| ------------------ | ------------------------------------------------------- | ------------------- |
| Todo               | Empty circle                                            | Todo                |
| In progress        | Ring with a right-half pie                              | In progress         |
| In review          | Ring with a three-quarter pie                           | In review           |
| Done               | Solid disc with a surface-coloured check                | Done                |
| Canceled           | Circle with slash                                       | Canceled            |
| Ready              | Status dot beside the word, on Todo tickets             | Ready               |
| Blocked            | Status dot beside the word, with the reason             | Blocked by T-KQ18   |
| Duplicate          | Circle with equals sign, beside a canonical-ticket link | Duplicate of T-KQ10 |
| Source unavailable | Status dot beside the words                             | Source unavailable  |
| Unread             | Status dot plus accessible unread state                 | Unread              |

Status rings have radius 6 and stroke 1.5; the inner pies have radius 3.75.
Done uses a radius-7 disc and a 1.6 check stroke. Todo and Done use
`--muted-foreground`, moving states `--foreground`, and Canceled and Duplicate
`--disabled-foreground`. These drawings do not take Lucide's global stroke.
A changed status sweeps clockwise in `--dur-4` (240ms) with `--ease-out`, following the owner’s DS4 resolution; Done fills
and its check draws in `--dur-settle` with `--motion-swift`. Initial glyphs and
recorded history stay still. Reduced motion makes changes instant.

`PlanRing` and `PlanSplitBar` are Plan-aware shared recipes in `features/plans`.
They consume `PlanCounts` from `show_plan`, including all non-trashed members,
independent of list filters. Countable work is Todo + In progress + In review +
Done; Canceled and Duplicate are excluded. The 16px ring (20px on Plans page rows)
uses radius 6, stroke 2, a `--track` track, a `--seg-review` arc for Done plus
moving work, and a round-capped `--foreground` Done arc on top, starting at the
top. The 6px split bar has a 3px radius and 2px gaps, with Done, In review and
In progress segments in `--seg-done`, `--seg-review` and `--seg-progress`; Todo
remains track. Zero countable work shows only track, including all-excluded
Plans. Both announce “Board polish, 0 of 5 done, 2 moving”, where moving counts
only In progress and In review. Decorative mode suppresses repeated speech.

Ready and Blocked are availability indicators, not extra statuses. Canceled and Duplicate must never look completed. Duplicate is a status of its own: it never looks Canceled or Done, and it always names its canonical ticket, or the source’s reference when that ticket is not in the workspace. Trashed tickets remain readable and show a restoration action; avoid a full-page faded treatment.

Each dot color keeps one meaning across every view:

| Dot    | Value     | Meaning                                                                                                                     |
| ------ | --------- | --------------------------------------------------------------------------------------------------------------------------- |
| Green  | `#45A557` | Ready, and other positive states such as an external source that is open and synced                                         |
| Orange | `#FF990A` | Blocked, and other states that need attention: Source unavailable, an unrecognized tracker state, an unresolved publication |
| Blue   | `#0062D1` | Unread                                                                                                                      |

Transient and settled states, such as Refreshing GitHub… or Closed on GitHub, use words without a dot.

## 3. Typography

Bundle Geist Sans and Geist Mono locally. Use the reference’s actual 400, 500, and 600 weights; include a real medium face before using 500. Do not synthesize 550, 650, or 700. Sans handles the interface and prose; Mono handles code, references, paths, and identifiers. Enable standard ligatures for prose, and preserve exact identifier legibility.

These next-generation roles are available to each surface as it is updated. Adding a role does not resize existing prose or titles. Keyboard chips always use caption size, including inside tooltips and buttons. Nothing is smaller than 12px. Display and document-title tracking use `--text-section-tracking` and `--text-doc-title-tracking`.
Use the source’s form tokens for shared inputs: 14px/20px default and 16px/24px large. Its observed native input size is 13.3px; ticketd’s themed form controls use the explicit 14px form token rather than relying on browser-native metrics. Root text size is 16px, so the reference’s `.875rem` form size resolves to 14px. The root stays 16px for rem maths, but `body`, dialogs, sheets, popovers and menus set the 14/20 working role, so text that no class sizes never renders at 16px; the 16px reading role is opt-in. Prose (paragraphs, captions, ledes, empty-state sentences) wraps with `text-wrap-style: pretty` and headings with `balance`, so blocks do not end in one-word lines.

Do not shrink the entire workspace to a 13px root or scale down type to fit an extra pane. Choose the appropriate existing role instead: captions are 12px, navigation, ticket rows, descriptions, and updates are 14px/20px in the working panes. Semibold is reserved for display/section-title emphasis; small section headings use the real medium weight.

Authored headings use these same roles: first-level headings may use the 32px section-title role, with lower levels using the 14px heading roles and spacing to express hierarchy. The ticket title remains the strongest application heading through placement. Preserve authored strong emphasis using the available semibold face without changing all surrounding interface labels to semibold.

List titles may truncate within their column; details show the complete title. Detail titles, validation errors, and consequential operation explanations wrap. Do not use compressed tracking on body text or reduce font size when a title is long.

### Tooltip

One tooltip in both themes, a small dark chip: `--tooltip` (`#171717` light, `#2E2E2E` dark) with `--tooltip-foreground`, 12/16 text, 4px 8px padding, `--radius`, at most 240px wide and wrapping, no arrow, and `--shadow-tooltip`, whose dark ring is the 14% `--shadow-border-base`. This replaces the reference's elevated white chip.

- **Motion:** after the delay the label fades in from 96% and a slight blur over `--dur-2`; beside a neighbouring control (the 300ms window) it opens at once with no fade. It leaves in `--dur-exit`.

- **Timing:** one provider for the app, 400ms before the first label and 300ms in which the next opens at once. A tooltip opens on hover and on keyboard focus only, never on focus that a closing menu or dialog returns to its opener, and closes when a menu, select or dialog opens over its trigger. With nothing to say it is not mounted, so it can never catch Escape.
- **Placement:** 6px from the trigger with 8px collision padding; below header and toolbar triggers, right of sidebar and rail triggers, above inline items. It never covers the row or line the pointer is on.
- **Content:** the label of an icon-only control, with its shortcut after it as inverted Kbd chips ("New ticket C"); the exact time on a focusable `<time>`; the full text of a truncated name, only while it is cut. A tooltip is never the only place an explanation lives, and a full path is shown in one but never used as a button's label. Native `title` attributes are banned on DOM elements by lint.

Do not use horizontal rules between document blocks or sections; space and the section heading set sections apart (see Ticket detail).

The reference's black-alpha drop layers vanish on `#0A0A0A` and `#171717`, so in dark the menu, large and tooltip elevations use `0 1px 2px #0000004D, 0 8px 24px -6px #00000080` after the 14% ring, and the modal adds `0 24px 48px -12px #000000A6`.

Overlay surfaces: menus, selects, listboxes and command lists use `--popover` with the menu elevation; popovers holding a form use `--popover` with the large elevation; dialogs and sheets use `--surface` with the modal elevation over the 80% canvas scrim. No rule may remove an overlay's shadow.

The document plane, ticket rows, and inline sections remain flat. Floating menus and dialogs use their corresponding elevation. Overlays always have an explicit opaque background and foreground, including when rendered through a portal.

Focus keeps the reference's look but is drawn with `outline`, never `box-shadow`, so it never shares a property with a control's edge or an overlay's elevation: `outline: 2px solid var(--ring)` at a 2px offset on free-standing controls, at −2px on rows inside lists and scrollers (where an outer ring would be clipped or cover the neighbors), and the 1px `--input-focus` outline on text fields. Focus is independent of hover and selection, and uses system-visible outlines under forced colors. After a pointer interaction the modality reset clears `outline` only, so a menu or button focused by script after a click keeps its shadow. Focus moved by script to a container or heading (a pane, a menu or dialog frame, a title after a bulk change, a mention target) never shows a ring. A guard test rejects focus drawn with `box-shadow`, a pointer reset that touches `box-shadow`, `inset var(--focus-ring)`, and any rule that removes an overlay's shadow.

### Opening, closing and full width

The layout always changes at once; the motion plays on top of it (section 12 holds the tokens and the language). Everything here is instant under reduced motion and while a key repeats or clicks come in rapid succession.

- **Opening a ticket.** The list narrows at once. The document glides in 16px from the right and comes into focus from a soft blur, on the smooth spring.
- **Closing.** The list takes the width at once. The document stays where it was, still showing the ticket, and fades out to a slight blur while drifting 8px right over `--dur-exit`. It takes no input while it leaves. It keeps the width it had beside the list (measured while the two sat side by side, since the layout has already changed when the exit starts), so it does not jump. On the board the peek fades out the same way.
- **J and K between tickets.** The open document fades out where it was over `--dur-exit`; the next fades up 6px from a soft blur over `--dur-enter`, after the first has gone. The old document is shown (inert, never `hidden`: the base layer's `[hidden]` rule is `!important`) while it fades out. The header changes at once. Choosing another row is the same swap. A held J or K swaps instantly on every repeat, with focus in the list or in the document. Closing a ticket and reopening one inside the 150ms close is not a swap: the pane's open glide plays alone, and the held document is not a ticket to move from. A ticket that loads after its skeleton (a link, the Inbox, a mention, no row to seed it) fades up from the soft blur over `--dur-enter` the moment it arrives, with no wait, because nothing is leaving; the skeleton glided in with the pane. It plays once per arrival, not each time the page is shown again.
- **Full width.** The list slides 12px left as it fades over `--dur-exit`, at the width it had, over the document, which re-centres with a 24px glide from the right, fading up from a soft blur on the smooth spring. Back reverses it: the list slides in from the left and the document glides 24px from the left, starting half visible because it was on screen a moment ago (the layout stall before the first frame would otherwise show a blank screen). Closing from full width fades the document at the full-width size, not the split's.
- **Narrow windows** use the same open and close; the document fades out over the list that replaces it.

Both the glide and the exit end on their own, so returning to the Tickets view never replays them.

### Responsive rules

Measure the available content panel width after navigation, not just the screen width. Preserve readable minimums rather than squeezing three panes together.

Pane breakpoints follow the pane's own width. The large panes (the ticket workspace, list, ticket and Chat documents, Documents, graphs and attachments) are not CSS query containers: WebKit restyles a container's whole subtree each time it resizes, which is every frame of the sidebar's fold or a split drag. `lib/width-queries` measures them instead and writes the breakpoints a pane is within to `data-width` (`[data-width~="max-799"]` where a query would say `max-width: 799px`). Only small containers, such as the sidebar, pane headers and the Chat tray, keep `@container`.

A workspace navigation sheet closes when the window becomes wide and stays closed on returning to narrow; its desktop sidebar preference and the responsive focus handoff are preserved.

A navigation sheet is at most 280px or viewport width minus 32px. Popovers retain 16px viewport clearance and collide away from edges. Forms that cannot fit a popover use a sheet/dialog with a scrollable body. At short heights, keep form actions reachable without clipping the body.

Switching pane modes, resizing, or opening navigation must not remount drafts, reset selection, or lose list scroll position. Horizontal scrolling belongs only inside code, wide tables, or the graph canvas. At 200% zoom, reflow the shell rather than shrinking the type. Native page
zoom uses the current webview's zoom API, from 50% to 200%; five Zoom in steps
from 100% reach exactly 200%. Mod+= or Mod+plus enlarges, Mod+minus reduces,
and Mod+0 resets to 100%, including while a field, rich editor, dialog or graph
has focus. Bare plus/minus remain canvas controls. One application handler owns
these keys; native automatic zoom hotkeys stay disabled. Requests serialize and
coalesce to the latest target, so reset cannot be overtaken by an older request.
Only confirmed native success updates the displayed percentage. Failure keeps
the prior zoom and offers Retry with the native cause under Details. Zoom is
window view state, never workspace data. The display-scale repair accounts for
intentional page zoom before comparing page and window bounds.

**Opening.** Settings opens on the page that needs the person (a problem to fix: Workspace sync stopped, a source that needs sign-in or is unavailable, the command line or an agent skill needing setup, Chats on with no agent that can start one); the first such page in nav order wins. With none, it opens on Set up ticketd while that is neither finished nor hidden, else on the page last used on this computer (`settingsPage` in the preferences; Set up ticketd, Search and a thing opened in place are never remembered), else on Appearance. A reminder (an update ready, detailed logging on) is marked but never takes Settings from the page last used. The rule is `initialSettingsPage()` in `settings-sections.ts`, the one place it lives.

The list lives in `settings-sections.ts`, with each page's one-line job (the lede under its title; About shows its wordmark instead); a page is added there with its file. The sidebar never lists individual things: a connection or an agent is a row on its page. **One model of what needs the person** (`settings-needs.ts`, read through `useNeeds()`) feeds the nav's marks, the sidebar's status line and the opening rule, so a problem is said once in each place and never differs between them. A mark is a 10px dot at the end of the page's row with a spoken label, and the page says the same words in the same tone: **Workspace sync** (sync stopped for the person: the sign-in ended, the folder is missing, storage is full, the service changed, the AWS CLI is unusable or the run failed, marked "Signed out", "Folder missing", "Storage full" or "Not syncing" as its status row says; offline and slowed down mend themselves and are not marked), **Command line** and **Agent skills** ("Needs setup": the tool is not found or needs attention; a detected agent lacks the skill or its copy needs attention), **Agents** ("Needs setup": Chats are on and no harness can start a Chat), **Ticket sources** ("Needs sign-in" or "Unavailable", as the list's rows say), **Diagnostics** ("Detailed logging is on") and **About** ("Update ready", "Update available" or "Update failed", once the notice that announced it was dismissed). Healthy pages carry no dot, and each page carries at most one. Pages that change what a mark reads ask for it again, so the dot follows without reopening Settings.

**Opening a thing in place.** A row that opens something (a connection on Ticket sources) shows it in the content area as a **drill-in** (`layout/SettingsDrillIn.tsx`): the panel bar gets a back chevron and a three-step breadcrumb (`Connections / Ticket sources / GitHub`), the sidebar keeps the parent page selected and gains no entry, and Back, the parent step or Escape (when no dialog or menu is open) return to the list. The open thing is the page id `source-<id>`; other ticket sources and agents use the same piece.

**Page shell.** A page is the panel bar and a centered column.

- **Panel bar:** sticky, 48px, with the breadcrumb `Group / Page` at 14/20 (group muted, page in the foreground color at 500) and an end slot. The end slot shows a source's save state on source pages and is empty elsewhere; there is no "Changes apply right away" note.
- **Column:** a 640px content measure, centred within a column with 32px side padding, 36px above and 80px below.
- **Page header:** the shared IconTile (40px, panel radius, recessed fill, border ring, 20px icon), the page title as the `h1` (24/32, 600) and a one-sentence lede (14/20, muted, at most 560px). The `h1` takes focus when a page opens; Search leaves the focus in the nav's field. A badge may sit beside the title.
- **Sections:** 32px apart. A level 2 heading row holds the title, an optional caption (12/16, muted, at most 520px) and actions at the end, such as Check again, Sync now or a status label; 12px separate it from the content.
- **Lists and rows:** a list is a surface with the panel radius and the shadow ring, its rows divided by the group hairline. A row has an optional leading IconTile (in a list every row has one or none does), a title (14/500) with a description (12/16 muted) and trailing StatusLabels and controls, all 32px (`sm`) and 8px apart, at least 64px tall with 12px × 16px padding. Focus inside a list is an inset outline. The top-aligned variant serves switches and wrapping text; the stacked variant serves full-width controls.
- **List footer:** a list may end in a recessed footer (12/16, muted) for explanations, results and secondary actions. Keep export and backup explanations and their success and failure messages in the footer beside their actions. A failed JSON export offers Retry, reopening the save chooser at the previous path before another write; canceling writes nothing.
- **Choices and controls:** use ChoiceTiles for an exclusive choice that deserves a title, a sentence or a preview, a segmented control for two to four short options, and a switch for an on/off preference. A switch’s thumb glides across on the glide spring while its track trades colour (`--dur-3`). A status is always a StatusLabel: a dot beside its word, never a coloured icon, bar, underline or tile corner. A path is PathText (file name, then its folder shortened in the middle, the full path in a tooltip) with Copy path and one RevealButton ("Show in Finder") beside it. A command to run is a CommandBlock, and ordered instructions are Steps.

**Saving.** Each page uses one of three models and says which.

- **Immediate:** Appearance, Attention, Files' destination and Agents apply when changed. There is no Save button and no note about it. A failure appears beside the control.
- **Save on blur:** a text value, such as the sync interval, saves when the field loses focus and says "Saved" beside it for two seconds. Drive keeps its failed name or interval draft, says "Not saved" in the reserved caption, and offers Retry for the same setting assignment. Editing that draft clears the old recovery action. Invalid input and failures are stated next to the field and the previous value stays in force; the next valid value clears the message, even when it is the value already saved.
- **Sources:** the Ticket sources page is one table of every source, with a row per connection and one for each source that has none yet, and the page for one source opens in place from its row. A connection's settings and Sync now action apply to that connection. A manual sync shows reported progress in the Sync status row and offers Cancel sync in the header until the run finishes. Under Sync, a saved connection's page has a Manage section: Rename keeps the connection's ID, Add connection starts another connection to the same source for a second account (its own form, then its page opens), and Remove… opens a destructive confirmation that explains what stays on the tickets and when sync can resume, then returns to the table.
- **Explicit Save:** a source is the exception. Its discovery rules are a draft with a save bar stuck to the bottom of the panel: a status (dot and sentence: Saved configuration, Unsaved changes, or the rules changed and need a new preview), **Discard changes**, **Preview matches** (hidden once the preview is current) and primary **Save**. Save stays unavailable until Preview matches has run for the current rules and something changed. Saving turns discovery on and says that matching issues are imported on the next refresh. A saved source also shows its sync schedule and when it last synced ("Synced 4 min ago"), with Sync now in the Sync header. Its Connection section keeps two facts apart: the saved connection ("Connected as X" or "Not connected", the words the ticket menu uses) and the account check ("Signed in as X").

## 11. Design system and shared components

ticketd's interface is assembled from one design system: the tokens in `apps/desktop/src/styles.css`, the bundled Geist fonts, and the shared React components in `apps/desktop/src/components/ui`, which are shadcn/ui copies restyled with the tokens. A web client can reuse them by building the same source; a separate package earns its place only once a second app imports the components.

### Levels

Build from the bottom up. A piece may use anything from a lower level, never from a higher one.

| Level                    | What lives there                                               | Where                            | Examples                                                                                                                                                                                                            |
| ------------------------ | -------------------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0 · Tokens               | Named decisions; the only place raw values live                | `apps/desktop/src/styles.css`    | `surface`, `muted-foreground`, `radius-panel`, `shadow-menu`, `text-ui`                                                                                                                                             |
| 1 · Base components      | One job each, no ticketd words, tokens only                    | `apps/desktop/src/components/ui` | Button, IconButton, Input, Select, Switch, SegmentedControl, StatusDot, StatusLabel, ChoiceTiles, CommandBlock, Steps, Badge, Reference, Count, Progress, Kbd, Tooltip, Skeleton                                    |
| 2 · Composite components | Content-agnostic compositions with slots                       | `apps/desktop/src/components/ui` | Field, Picker, ChoiceList, TagPicker, Menu, Popover, Dialog, DialogShell, Sheet, Command, ListHeader, PaneHeader, PageHeader, EmptyState, Alert, StatusLine, SectionHeader, Card, Item, Timeline, EventRow, Sidebar |
| 3 · Product components   | ticketd recipes that know tickets, statuses, sources and Plans | `apps/desktop/src/features`      | StatusIcon, TicketRow, TicketPicker, RecordPicker, property bar, Activity, source card, Filters and Display, bulk bar                                                                                               |
| 4 · Layouts              | Page structures that place components                          | `apps/desktop/src`               | App shell, split view, ticket page, management page, Settings                                                                                                                                                       |
| 5 · Screens              | Real screens with real content                                 | `apps/desktop/src`               | All tickets, a ticket, Inbox, a Plan                                                                                                                                                                                |

Levels 0–2 live in `components/ui` and `styles.css`; levels 3–5 live with their features. Interactive components wrap a Radix primitive (Select, Popover, Dialog, DropdownMenu, Switch, Tooltip) that supplies keyboard, focus, and ARIA behavior; features use the wrapping component and never style a Radix part directly. Recurring combinations of components are patterns, written in this document rather than coded: empty, loading, and failure states (section 12) and the choice between menu, popover, and dialog (below).

### Catalogue notes

What the shared pieces do and which variants exist; each has a JSDoc summary in its file.

### Tokens

Primitive values, such as hex colors and pixel sizes, belong only in the token blocks of `apps/desktop/src/styles.css`. Components use the semantic tokens of sections 2–4, such as `background`, `surface`, `recessed`, `foreground`, `muted-foreground`, `accent`, `border`, `link-foreground`, `error-surface`, `status-ready`, `text-ui`, `radius-panel`, `shadow-menu`, and `focus-ring`. Component tokens exist only where a part needs its own role (`sidebar-*`). Light values sit on `:root` and dark values on `:root[data-theme="dark"]`. `[data-theme-preview="light"|"dark"]` on any element applies that theme's tokens, derived ones included, to its subtree, so a preview, such as Appearance showing both themes, uses tokens and no raw colors; inside it use tokens, not `dark:` utilities. Tailwind's theme maps the color tokens to utilities such as `bg-accent`; spacing and control sizes use Tailwind's 4px steps with the values in section 4.

### Rules that keep the system small

- Check the catalog first. Extend an existing component before adding a near-duplicate, and never give two components one name.
- Build a new piece inside the screen that needs it. Promote it to level 3 on its second real use with the same meaning, and into `components/ui` only when it carries no ticketd words.
- A variant keeps the component's anatomy and behavior and differs in function; otherwise make a separate component or a recipe.
- Put content in children or named slots. Use typed props only for design-decided options such as `variant`, `size`, or a leading icon, and start them narrow: opening an API later is easier than closing it.
- Reference semantic tokens only: no hex values, no magic numbers, and no `!important` overrides of a shared control from a feature stylesheet.
- Stay on Radix. When adopting a shadcn/ui component, copy its Radix variant and restyle it with the tokens.
- Feature stylesheets own layout. Visual roles for the updated screens live in `components/ui/surface-roles`, imported by their existing layout stylesheet so selectors, source order and lazy loading remain stable. Token definitions remain in `styles.css`.

### Checks

`./scripts/check` enforces the tokens and components mechanically, and every count it keeps may only fall:

- ESLint runs `@shadcn/lint` on app components. It reports raw palette colors, arbitrary values, restyling a shared component beyond layout classes, and classes it cannot read, and its messages name the variant, size, or token to use instead. Findings that predate these rules are recorded in `apps/desktop/eslint-suppressions.json`; after fixing one, run `npx eslint --prune-suppressions` in `apps/desktop`.
- `src/test/design-tokens.test.ts` counts raw colors, literal radii, and `!important` in each stylesheet; `src/test/type-scale.test.ts` keeps font sizes on the type scale.

### Recorded lint findings

`apps/desktop/eslint-suppressions.json` holds the findings that remain; each group below says why it stays. Fix them by the route given, and prune the entry in the same change.

- **Feature class on a shared component** (the `no-restyle` entries in `src/features` and `WorkspaceSidebar.tsx`, such as `board-card`, `filters-content`, `linked-work-title`, `plan-actions-menu`). The feature stylesheet gives the component its own height, padding, font size, background or width, and many of the components render in a portal, so no parent element exists to carry the class. Each needs a variant or size on the shared component that the design names; moving the class to a wrapper would only hide the restyle. Do them one component at a time, with the screen open in both themes.
- **Overrides inside `components/ui`** (`command`, `empty-state`, `field`, `picker`, `resizable`, `sidebar`). The composite passes spacing, type or color classes to the primitive it wraps (`Label font-normal`, `CommandItem` padding). Each becomes a variant on the primitive (`dialog`, `label`, `separator`, `sheet`, `input`).
- **Arbitrary values with no scale equivalent** (`sidebar.tsx`, `switch.tsx`, `empty-state.tsx`): `calc()` widths and offsets, `transition-[...]` property lists, `0_0_0_1px` ring shadows, `tracking-[-0.6px]`, `stroke-[1.75]`. They need a new token or utility, which the design has not decided.
- **Toggled state color** (`Activity.tsx` `bg-accent` on a ghost Button): needs a pressed treatment for ghost buttons, which would change every ghost trigger that opens a menu.

### Control and state recipes

Compose a control before inventing another. Inputs, buttons, menus, fields, notices, and dialogs must have one visual contract across views.

| State          | Required treatment                                                                            |
| -------------- | --------------------------------------------------------------------------------------------- |
| Rest           | Clear label, semantic surface and foreground, stable dimensions                               |
| Hover          | Subtle neutral fill or border change; no translation or scaling                               |
| Keyboard focus | Visible outline ring independent of hover and selection (section 4)                           |
| Pressed/open   | `--accent` fill and semantic expanded/pressed state; never the primary fill                   |
| Disabled       | Native disabled semantics, no activation, readable label without opacity; explain why         |
| Pending        | Preserve width, show progress text/icon, block duplicate submission, retain the draft         |
| Invalid        | Field-level message and invalid semantics; never only a red outline                           |
| Failure        | Actionable local error with retry where possible; distinguish failed saves from saved content |
| Success        | Updated value and concise confirmation; avoid repeated success toasts for autosave            |

Primary buttons use the inverted neutral pair. Destructive buttons sit on `--error-surface` with the `--destructive` label, and hover adds a 1px `--destructive` ring; a destructive confirm places Cancel before it. Secondary actions use outline or quiet neutral fill. Tertiary actions use ghost styling with a visible focus state. Inline ticket references are links with consistent hover/focus behavior; they should not resemble a row of submit buttons embedded in prose.

Fields have persistent labels; placeholders are examples, not labels. Forms use aligned full-width inputs, shared field spacing, and a trailing action row. Put the destructive action away from ordinary submit controls. Do not place an unstyled native select beside a themed button and consider the form finished.

Menus are for short action choices. Popovers are for small, focused edits. Dialogs are for multi-field forms, consequential confirmation, and dependency review. Every dialog/sheet has a title, a close path, correct focus containment, and focus return. Escape closes only the foremost surface and must not silently discard a draft. The caret-anchored Insert block popover consumes Escape at its Radix layer, retaining the rich editor, caret and draft beneath it, including inside New ticket and Capture. A status line handles Escape from its own DOM controls; Escape from its portaled failure Details closes only Details, returns focus to its trigger and retains the error with Retry. One action must not open a stack of overlapping editors.

### Menus, selects and choice lists

- **Placement:** below the trigger, flipping above only on collision, 4px away with 16px clearance, at least as wide as the trigger, inside the nearest OverlayBoundary so nothing escapes over the sidebar or covers its own pane's header. A select list never opens over its own trigger.
- **Surface:** `--popover`, `--radius-panel`, 4px padding, `--shadow-menu` (`--shadow-large` for a popover holding a form). Menus are 220–280px wide by content, pickers 280–320px; lists stop at 320px and scroll inside.
- **Rows:** 32px (36px in ticket and record pickers): a 16px icon, the label, muted meta or a Kbd, and a trailing check for the current value. Every row of a list has an icon, or none does. The highlight is `--accent` for pointer and keyboard alike: with the keyboard it is the `Glide` that travels from row to row (one group per open menu, select or list, through `RowHighlight`), with the pointer a plain fill that follows at once; section labels are 12/16 muted; separators are hairlines.
- **Values:** a single choice opens with its current value highlighted and checked, so Enter never clears it; the clearing choice ("No project") comes last after a separator. A multi choice (tags) stays open and toggles checks.
- **Disabled and destructive:** a disabled row keeps a readable `--disabled-foreground` label and says why on a 12/16 line under it, with no opacity. Destructive rows go last after a separator.
- **Rules:** a menu holds choices or actions; a popover holds a small form or a list and has a title when its trigger is icon-only; no popover is a column of buttons. Never a one-item menu: make that action a direct button. "…" only gathers several unrelated actions.
- **Search and empty:** an optional 32px search row at the top, a quiet "No matches" row, and "Create “x”" as the last row where creating is allowed. Pickers say "Search {things} by title or reference".
- **Pickers:** TicketPicker looks an exact reference up first, waits 150ms after typing, and shows a fixed list of six 36px rows (three in the compact Link a ticket dialog; StatusIcon, reference, title, a caption such as "Linked") with "No tickets match “x”"; its multi-pick form checks rows and its dialog puts the count in the note slot. RecordPicker groups tickets, Documents and Projects as "Linked to this …", "Recent" and results for `#` mentions, Link popovers, Plan context and the editor's Link.

### Dialogs

- **One component:** DialogShell, in three sizes: `sm` 480 for a confirm, `md` 640 for a form or picker, `lg` 920 for review and compare. A multi-step flow keeps one size. New ticket starts at 640px and expands to 760px, bounded by the viewport, while keeping the draft and the same top anchor. The attachment and diagram previews use the `viewer` size, top 40px, min(1200px, 100vw − 48) by 100dvh − 64 (12px from every edge under 880px), with one header row (its actions, then Close) and no footer. A review with nothing to confirm (an empty Clean up) leaves the primary out and keeps one dismissing button. A view switch inside a dialog (Attach file's Upload, Existing files, Google Drive) sits under the header in the `tabs` slot and keeps the dialog's height.
- **Position:** anchored at max(48px, 12vh) and growing downward; the body scrolls inside while the header and footer stay put. A dialog never re-centres while someone types, searches or chooses. Controlled dialogs capture their invocation before menus unmount, return focus to the connected trigger, and keep it as the opener. The panel rises `--motion-rise-overlay` from 98.5% and a soft blur on the smooth spring, from its top anchor, and leaves in `--dur-exit` fading to a slight blur; its scrim fades in over `--dur-3` and out in `--dur-exit`. New ticket's size glides from 640 to 760px wide and to its full height on the smooth spring, only when Expand or Collapse is pressed (the dialog is marked `data-resizing` for the spring, so a window resize never animates it; the height needs `interpolate-size`, so a webview without it snaps the height), and it never re-centres vertically. All of it resolves instantly under reduced motion and key repeat. Closing content is inert and remains in Radix Presence until its exit completes. Conditional form and review owners release themselves through `onExitComplete`; the attachment viewer uses the same Presence completion before releasing its media. New ticket keeps a render-only closing snapshot independently of its recovery draft. Capture finishes saving or protecting its draft before starting the exit. Focus already placed in another pane or overlay wins over an older return target; responsive chrome can resolve the current logical opener at completion.
- **Header:** a 24/32 title naming the action and its target, an optional one-sentence description, and the 32px close button on the title line, with 24px padding. A confirm's title is a question ("Change T-FV10 to In progress?").
- **Body:** a 24px inset; labels above 40px fields; pickers stacked; notices as Alerts.
- **Footer:** a 56px minimum band on `--footer-band` under a hairline. At the left, one persistent control (the Create more switch). At the right, the note slot (12/16 muted: the blocked reason such as "Add a title to create.", a count, or a transient result such as "Created T-FV16 · Open"), a ghost Cancel, and one 32px primary, default or destructive, with its key hint. The primary repeats the verb and keeps a constant label; counts go in the note slot. Never a close button plus "Done".
- **Failure:** the dialog stays open and a compact error Alert appears above the footer.
- **Focus and stacking:** focus starts in the first field, or on Cancel for a destructive confirm, and returns to the opener. Never open a dialog from a dialog: replace its content instead.

## 12. Feedback, motion, and accessibility

Use a small set of observable states rather than transient notifications everywhere. Empty, loading, unavailable, failed, saved, and externally changed data must be distinguishable. Build them from the shared EmptyState, Skeleton, Alert and StatusLine components.

Feedback has three tiers, and nothing is inserted into the flow to report an outcome:

- **Status line** (per pane; the one transient surface): outcomes of an action, such as moved, removed, copied from a menu, created, or a link that couldn't open. It floats at the bottom centre of its pane, 8px above the edge (above a docked bulk bar), 40px tall and at most 480px wide, on `--popover` with `--shadow-menu` and `--radius-panel`: an optional 16px icon, the message in the past tense with the reference ("Moved T-KQ16 to In progress"), one ghost action (Undo, Open, Retry, Copy link) and Dismiss. It lasts 4s, 10s when it carries Undo; a failure stays until dismissed or retried and is `role="alert"` with the attention dot, others `role="status"`. Hover or focus pauses it; one shows at a time and the newest replaces it; closing it keeps focus in the pane. It is never used for autosave, and is never stacked. Motion: it rises 8px from a soft blur at the bottom of its pane; Undo, Dismiss, the timeout or the next outcome fades it out in 150ms, and it cannot be pressed while it leaves. A following outcome keeps the same line and crossfades its words and action rather than stacking a second line. In a Chat the edge is the tray: the line rises from the transcript's bottom edge, centred on the tray and 8px above its top, so it never covers the composer's controls, and follows the tray as its height changes.
- **Alert** for lasting conditions where they apply (in Trash, outside the results, source unavailable, couldn't save).
- **Workspace band** for workspace-level state only (read-only, locked, disk full).

Reversible changes act at once and offer Undo in the status line ("Moved T-KQ1 to Trash · Undo", "Removed the link to T-KQ11 · Undo", "Unlinked Spec · Undo", archiving or trashing a Chat); a failed Undo becomes the failure with Retry. Irreversible changes are confirmed first.

Public errors use the shared failure description. Source refresh reports, persisted source failures, publication review, Automation settings and ticket-run actions keep transport diagnostics under an actual Details control. Publication eligibility remains domain copy. Confirmed publication stays confirmed if a following read fails, with Check saved state as a read-only recovery action. Unknown outcomes, including unclassified lost replies, block another publish and require checking the saved ticket and resolving any retained publication attempt; only a definite Core refusal allows publishing again. Run again keeps the original action disabled through its authoritative saved-run refresh after failure. If that read fails, Check saved runs retries only the read; a successful authoritative read establishes the outcome before another run can be started. Dismiss retries the same run identity. Bare one-line errors never promise a Details action they do not render.

Empty states follow one copy registry (`lib/empty-copy.ts`): "No {things} yet", "{Place} is empty", "No {things} match “…”", then one sentence on what appears here and how it gets here; never "scope", "eligible" or "snapshot". A primary action only when it is the only way to fill the view and no other primary is visible; otherwise outline sm, and none when the header already holds the action. Chrome that acts on nothing is hidden: no count, Search, Filters or Display over an empty workspace or Trash, and no Refresh there unless a source could bring tickets in, so a first run shows the title, one block empty state and its primary "New ticket C"; no pager, Clean up or count footer at zero. Placeholders appear only after 300ms and never pulse; once they show, a soft sheen of `--hover` travels across them (`--dur-sheen`), and row placeholders fade up from a blur one step apart. Paging is one "Show 50 more" under the content; totals sit in headers. An empty state carries the action that fills it; two have none because the control sits directly beside them: the Activity timeline (its composer is the row above) and a Plan’s Dependencies view (Add tickets is in the Plan header above). An empty Board column says “No tickets” in one muted line (its header names the status and holds Add); with a search or filter on it says “No matches”. When nothing matches at all the board shows the view's one empty state instead of empty columns.

| Situation                       | Presentation                                                             |
| ------------------------------- | ------------------------------------------------------------------------ |
| Initial list load               | Row-shaped placeholders using the final row geometry                     |
| Background refresh              | Retain the current content and scroll; avoid blanking the pane           |
| No tickets                      | Short explanation and New ticket action                                  |
| No filter matches               | Current query context and Clear filters                                  |

Counts remain unknown until their own read succeeds. Initial failures retain an unknown count and expose the read's Retry; a known empty answer is distinct from pending or failed reads. Background failures retain observed content and counts. Document Trash applies only its latest read: a pre-Restore response cannot replace post-Restore rows or consume that action’s focus. Focus moves to the remaining Restore row (or Open when empty) only after the latest post-Restore read and only while the person has not moved focus elsewhere. Plans reads are independent of ticket-list reads and use still card-shaped placeholders after 300ms. Document reader opens keep their target and failure independently of navigator reads, so a successful Recent/Pinned refresh cannot dismiss an open failure or redirect Retry.

### Failures and error language

One cause is reported once, at the place it concerns, in plain words. The core sends each failure with a kind (`workspace_read_only`, `workspace_unreadable`, `workspace_locked`, `disk_full`, `not_found`, `cycle`, `conflict`, `too_large`, `not_signed_in`, `offline`, or `failed`); the interface chooses its words and next step by kind and never parses the message. `describeFailure(error, action)` in `lib/api/describe-failure.ts` returns the title, sentence, next step, and raw text, and lint rejects raw `String(reason)` text in the interface. Unclassified bridge failures use a safe, action-specific title and say that the result could not be confirmed, with a retry or Details step. Arbitrary host text stays behind Details, and no unknown mutation failure claims that nothing changed. History uses this same failure description for reads and restores: its failure shows in the dialog's error row above the footer, with no empty band under the header while nothing failed, Details opens over the content, and Retry repeats the selected restore request with the same request ID. The selected version and current comparison stay in place. The list and comparison have a height of their own and scroll inside it, so older versions arriving never move the footer, and a version kept in a storage is captioned "Kept in" and its name ("Kept in S3", "Kept in Google Drive"). Below 600px, the versions list sits above the comparison so both values retain readable columns.

- **Voice.** The title says what did not happen: “Couldn’t {verb} {object}”, sentence case, no period. One sentence follows with the plain cause and what is safe (“Nothing changed.”, “Your draft is kept on this device.”). The action is “Retry” only when retrying can succeed; otherwise it is the fix (“Choose another ticket”, “Sign in again”). Core prefixes, “Error:”, CLI commands, backticks, byte counts, and absolute paths never appear outside Details.
- **Loading geometry.** Empty status announcements may collapse, while shared Skeleton placeholders retain their reserved geometry. Linked relationships show their still skeleton after 300ms until the read settles; the empty-status rule never hides that visual placeholder.
- **Details.** The raw text sits behind a “Details” toggle, in 12px mono with “Copy details”. Status-line failures retain the same diagnostics in an anchored popover, keeping the line at 40px while Details is open.
- **By scope.** An invalid field shows a FieldError under it (`aria-invalid`, nothing is sent): an empty ticket title says “A ticket needs a title.” and keeps the last saved title. A failed action shows a compact error Alert under its control or above the dialog footer (FailureAlert). Dense rows and the ticket rail show one caption, “● Not saved · Retry”, with the cause under Details (FailureCaption). A region that cannot load shows “Couldn’t load {things}” with Retry in place of its content and never claims to be empty (FailureState). A failed background refresh keeps the content with “Can’t refresh. Showing the last list. Retry”. A dialog whose main task is blocked shows an error Alert at the top of its body.
- **Workspace band continuity.** A workspace failure blocks writes and announces its truthful message immediately. Each pane or page header keeps a reserved 28px notice-control slot from its first frame, before its existing right actions; healthy headers leave it empty, without a blank band above the document. When a failure arrives under pointer or focus, the slot shows a keyboard-reachable warning control with the full message as its accessible name and tooltip. It opens the real band content, Details and Retry in an anchored popover; “Review workspace notice” is also offered in the palette. The same mechanism covers the legacy-draft notice, with failure taking priority. The full 40px band commits on navigation or genuine departure from the content, including explicit pointer or focus departure outside the pane and its overlays. A disabled field falling to BODY is not departure. Successful recovery clears error wording immediately; an occupied 40px layout slot remains empty until departure so Retry never pulls the document upward. Pointer or focus still over the document, including focus moved to Retry, keeps that session's geometry. The shell never covers existing controls or body text to report the failure.
- **Workspace band.** Workspace-level state only (read-only, locked, unreadable, disk full, unsaved drafts not protected) is one 40px band inside the top edge of the content panel: `--workspace-band` (`--recessed` in light, approved `#1D1D1D` in dark) with a bottom hairline, an attention dot, one sentence (“This workspace is read-only. Changes can’t be saved.”), Details, and Retry. There is at most one; it stays until Retry succeeds. Details opens the shared anchored failure popover, preserving the band’s 40px height and the panes beneath it. At narrow widths the sentence truncates visually with its full text available to assistive technology and in its tooltip; Details and Retry stay on the same line. Successful reads never dismiss a workspace failure, including a lock. Retry keeps the band while queued draft protection settles and the existing sidebar query proves write access through its reminder transaction. Only the failure observed at the start of recovery can be cleared; newer failures remain. Startup recovery uses the same write proof before clearing a stale failure band. The one lasting workspace notice that is not a failure, the legacy-draft review, uses the same band with a neutral dot and its one action ("All desktop profiles reviewed"), and gives way while a failure band shows. Nothing else repeats the cause: editors add no notice of their own, and editing controls rest disabled with the reason.
- **Startup.** When the workspace cannot be opened, the window shows a recovery screen in the app’s theme (the native title bar included, with best-effort native theme and canvas requests from the blocking bootstrap even if application modules fail): one 520px column 120px from the top with the wordmark, an alert IconTile, “ticketd can’t open this workspace” at 24/32, the plain cause, the workspace file as PathText on `--surface` with Copy path and Show in Finder, Retry, and Details on its own line. Restore from a backup and Choose another workspace are not offered there: a restore needs a readable workspace for its safety copy, and the workspace location is fixed.

### Motion

Motion is **Refined**: calm, continuous and never showy. Two earlier directions were rejected in review: Calm (short fades that read as faint) and Expressive (springs with bounce, tilt and rolling counts).

- **Movement** glides on a spring with no bounce. Nothing overshoots, tilts, stretches or rolls.
- **Appearing:** things fade up from a soft blur and settle 6px (rows) or 8px (messages and overlays) below their place. **Leaving:** things fade out to a slight blur, faster than they arrived.
- **Continuity only where it helps.** Highlights travel (sidebar, tabs, menus, the palette). Moved items glide to their new place (rows, cards, the document).
- **Rules that stay.** Buttons and links change color/background without scale, translation, or opacity animation. Nothing moves under the pointer. Key repeat and rapid clicks land instantly, and a new change interrupts a running one. Nothing animates while a panel is being resized. Reduced motion makes every change instant. Motion never conveys completion or selection by itself.

| Token                                    | Value                                     | Use                                                                                                    |
| ---------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `--spring-glide`, `--spring-glide-t`     | no-bounce spring, 0.30s; settles in 366ms | Highlights and indicators that travel                                                                  |
| `--spring-smooth`, `--spring-smooth-t`   | no-bounce spring, 0.36s; settles in 440ms | Moves, entrances, opening and closing                                                                  |
| `--spring-travel`, `--spring-travel-t`   | no-bounce spring, 0.46s; settles in 562ms | Long moves: a card to another column, a row to another group                                           |
| `--dur-enter`                            | 240ms `--ease-out`                        | Opacity and blur of an entrance                                                                        |
| `--dur-exit`                             | 150ms `--ease-in`                         | Exits                                                                                                  |
| `--motion-blur-in`, `--motion-blur-out`  | 4px, 2px                                  | Entrance and exit blur                                                                                 |
| `--motion-rise`, `--motion-rise-overlay` | 6px, 8px                                  | Entrance offset for rows; for messages and overlays                                                    |
| `--stagger`, `--stagger-steps`           | 24ms, 7                                   | Cascade step: header first, then rows; the cap, so at most eight steps (JS and CSS read the one token) |
| `--dur-sheen`, `--dur-shimmer`           | 1.6s, 1.8s                                | Skeleton sheen; the “Working” shimmer                                                                  |
| `--dur-theme`                            | 280ms `--ease-in-out`                     | Whole-window theme crossfade                                                                           |

A spring token is a CSS `linear()` easing sampled from a critically damped spring (bounce 0); its `-t` token is the time the curve takes to settle, which is what a duration means for it. Every CSS motion duration and delay uses a token. The earlier timings stay: `--dur-1` 80ms for press and color feedback, `--dur-2` 140ms for reveals and status lines, `--dur-3` 180ms for menus and popovers, `--dur-4` 240ms for dialogs and glyph sweeps, `--dur-lift` 120ms, `--dur-settle` 160ms, `--dur-arrival` 1200ms for an arrival highlight, `--dur-loading-delay` 300ms for skeletons, `--dur-spin` 900ms for a spinner revolution and `--dur-instant` 0ms. Entry uses `--ease-out` (`cubic-bezier(.16, 1, .3, 1)`), exit `--ease-in` (`cubic-bezier(.4, 0, 1, 1)`). The existing `--motion-swift` is reserved for the Done check. Tailwind transition and spinner defaults use these tokens too.

**Split.** CSS with tokens does fades, blur, expand and collapse (`grid-template-rows` 0fr to 1fr), the skeleton sheen, the shimmer and the theme crossfade. The `motion` library does springs, layout moves (rows, cards, regrouping), shared highlights (`layoutId`), `AnimatePresence` for page and view switches, and cascades. Its timing comes from the tokens: `lib/motion-tokens` reads them when a motion starts, so no duration is copied into JS. View Transitions are not used: they are unproven on WKWebView and WebKitGTK and queue updates behind a running animation.

**Primitives** in `components/ui/motion` are what surfaces use; none takes a duration. One `MotionProvider` at the app root loads the library (`LazyMotion` with `domMax`, components use `m`), follows the system's reduced-motion setting and installs the input guard.

- `Presence` and `Appear`: enter and exit, fade up from blur and leave fast. `index` places an item in a cascade.
- `row-motion` (`components/ui/row-motion.ts`): the same entrance, exit and glide as props for a list item, because `Appear` is a `div` and a list's item must be the `li`. Every list's rows (tickets, Inbox, Chats, Activity, linked tickets, board columns, the loading placeholders) are built from it. The stagger delay sits inside each property's transition, settled rows drop their filter, and a glide takes a `layoutDependency` (the order) so rows are measured when the order changes, not on every render. The ticket list and its placeholders, the long lists, read the motion tokens once per render with `rowTokens()` and hand the snapshot to each helper, so they cost a handful of reads, not one per row; the shorter lists (Inbox, Chats, Activity, linked tickets, board columns) leave it out and each helper reads the tokens itself. An Inbox entry builds its arrival only when it mounts arriving. `data-arriving` means one thing, a page arrival; a released row's arrival fill is marked `data-arrival-fill`.
- `Glide`: the highlight that travels between items (`layoutId`). The item needs `position: relative`, and the container of all the items, never each item, is `isolation: isolate` (the sidebar body, the Settings nav, the ticket list's rows, a menu, popover or command list, a segmented control): the highlight is `z-index: -1`, so with an isolated item it would sit above every earlier item it passes while travelling down and blank their labels. The open ticket row clears its own hover fill so that the highlight shows. A list that scrolls its rows is a `layoutScroll` host (`scrollHost`, used by the menu, sub-menu, select and command lists) so the highlight measures its old row against the scroll. A disabled menu row renders its highlight after its children, so the icon stays `:first-child` for the reason indent.
- `Expand`: height that opens and closes on the smooth spring.
- `CrossfadeText`: words that change in place.
- `Arrival`: the `--hover` fill fading over `--dur-arrival` behind what just arrived.
- `DrawnPath`: a line or check drawn along its length (`stroke-dashoffset`).
- The Skeleton sheen and `Shimmer` (the “Working” step).

**Instant.** Reduced motion zeroes every duration, delay, offset and blur token, including in theme previews, disables animations, and leaves spinners as static rings. The input guard (`lib/motion-guard`) does the same while a key repeats or clicks are rapid: it marks the document `data-motion="instant"`, which zeroes the same tokens except the skeleton delay and the spinner, and the motion library skips what it would start next. A running CSS transition keeps the timing it started with and a started library animation ignores the flag, so when the guard engages it also finishes both by hand: every finite CSS transition and animation (`document.getAnimations()`), and the library's running animations (found through its inspector hook, `__MOTION_INSPECT__`, which announces each start with the live handle and is pinned with the exact `motion` version). Only the press that engages the guard finishes motion; the next change still interrupts one that is running. A held J or K, or typing ahead, never queues motion behind the input.

**Shell motion.** The window's own surfaces:

- **Switching pages.** The sidebar highlight is one `Glide` that travels to the row of the new page (it sits beside the row's button, which clips its text), and the row's text color changes over `--dur-3`. The pages sit in `ViewRegion`, a wrapper that adds no box. Pages stay mounted and toggle `hidden`, or mount per visit; either way the old one is gone from the document when the new one commits. So before React updates the DOM the region copies the page on show, then lays the copy over the panel as an inert, hidden-from-assistive-technology still picture that fades out to a slight blur over `--dur-exit` (never taking the pointer). The new page waits that long, then arrives in two parts: its `[data-arrive="header"]` (the page and pane header components mark themselves) fades up from the soft blur and 6px below, then the visible `[data-arrive="row"]` elements (ticket rows, Inbox entries, Chat rows; rows below the fold and placeholders are left out) follow in document order one `--stagger` apart, eight steps at most, later rows arriving with the last. What carries no marker (a group heading, a switch at the foot) is not left showing over the picture: the page itself is held at nothing until the arrival starts and fades in with the header. A page with neither marker fades up whole. With no picture on show (the page before it was not there to copy) there is no old page to wait for, and the arrival starts at once. While it plays, the page root carries `data-arriving`, which in-list cascades check so they do not play on top of it. A page that choreographs its own entrance (Plans, Projects, Documents, Automations, Settings, the First-run guide) marks its root `data-own-entrance`: the old page still fades out, the new one is not animated, and its own cascade starts once the old content is gone (after `exitDuration()` when a switch reveals it, at once when it mounts). A marker on something that is leaving (`data-leaving`) does not count, and a page that is leaving is not arrived at. The Projects page host has a real box, not `display: contents`, so it can be copied and animated like the rest. The copy lays out like the live page: its ids are renamed `data-view-id` (so `getElementById` never finds it; `data-id` is the rows' own), the rules that key on a panel id (`#list`, `#detail`, `#chat-list`, `#chat-detail`) also match `[data-view-id="…"]`, and SVG ids stay so `url(#…)` still resolves. Moving between Tickets and the Inbox, opening and closing a graph, and the First-run guide giving way to the list (the guide is no longer rendered, so its picture is the one fade; the list arrives as above) switch pages too. With reduced motion, or during a held key or rapid clicks, there is no copy and no wait.
- **Collapsing the sidebar.** The width and padding move on the smooth spring. The labels, the wordmark and the shortcut stay in their rows and fade to a slight blur over `--dur-exit` while the narrowing clips them; expanding opens the width first, then fades them back: the sidebar is a size container (`container-type: inline-size`) and everything the rail drops (labels, wordmark, group headings, counts, the search entry's words) stays hidden at once while it is narrower than 185px, so the width itself is the clock and a busy main thread cannot let a label show beside the 56px rail. The rows keep their elements through the fold (the folded rail's tooltip stays around the button, held shut while expanded), so a label that fades out is the one that fades back in. Icons keep their column. The wordmark and the top buttons sit at explicit places, so the New ticket button drops a step, the collapse button takes its place, and everything below follows the top row's height, all on the smooth spring. The two buttons cross paths, so they never move together: folding, New ticket drops and the collapse button slides over after it; unfolding, the collapse button leaves the corner and New ticket climbs after it. The Projects and Plans groups arrive late (once the workspace says it has any) or leave through `ArrivingGroup`, which opens or closes their height and fades on the same spring, so the rows below glide instead of being pushed down in one frame. The footer's Settings and Trash sit at explicit places too, so the row and the column are one transition. Projects and Plans each fold through an Expand pair (`FoldingGroup`): the list closes while the icon menu opens, on the same spring, so the groups below glide with the height; the side that leaves stays mounted and inert until it has closed. The ticket pane decides its narrow layout from the settled width (`useNarrowPane` waits 120ms for the width to hold still), so the sidebar's width spring never flips it halfway.
- **App launch.** The sidebar fades in; the content pane follows a step later, then the pane's header and visible rows (the same `data-arrive` markers as a page switch) in a cascade one `--stagger` apart (at most eight steps), and the pane carries `data-arriving` until it settles. It plays when the window opens and after a workspace switch (once the replaced Workspace's reads are dropped), never when returning to the window. It does not wait for the list: rows that arrive after the first paint replace placeholders and belong to the list, not to the launch, and a row that is already animating (the list began its own cascade first) is not started again. A pane that shows a page owning its entrance (the First-run guide) does not fade and has no header or row cascade stacked on it: only the sidebar fades in.
- **Command palette.** It opens and closes through the shared dialog. Results that were not on show settle in top first, a stagger step apart, when the query changes; the opening, a list that returns when the query is cleared, and results already on show do not replay. A held key makes them land at once.
- **Navigation sheet.** Below the wide layout it glides in from the leading edge on the smooth spring over a scrim that fades in over `--dur-4`; it slides out over `--dur-exit` on `--ease-in` and the scrim fades over `--dur-exit` with it, never after it.
- **Workspace band.** The slot beside the top of the content panel opens by height on the smooth spring (its 40px is a block inside the Expand body, so the track has room to interpolate; a `min-height` on the body would start it at 40px) and closes the same way, with everything below moving with it; the message fades in from a soft blur, and when the condition clears it fades out over `--dur-exit` while the strip stays (nothing moves under the pointer). It follows the reservation (`use-band-continuity`), not the condition, so it never opens or closes under the pointer.
- **Counts.** `Count` crossfades a number or word that changes, which gives the sidebar, headers, columns and queues the same behavior.

Menus, submenus and popovers enter over `--dur-3` with a tokenized 4px slide from the trigger side, scale .98 and a 2px blur; their distinct exit animation fades to .98 and a slight blur over `--dur-2`. Closing menus, popovers, selects and sheets remain inert until Presence removes them. Activity hover actions stay in keyboard order and reveal on row focus; the confirmation keeps its action exposed through focus return, and a newer focused control keeps focus when an older overlay finishes. The navigation sheet is the exception to the rise: it glides in from its edge (see Shell motion) and shares the `--dur-exit` exit. Dialog/palette rise and scale use `--motion-rise-overlay` and `--dialog-scale`; all offsets and durations resolve instantly under reduced motion.

## 13. Implementation boundaries

`apps/desktop/src/styles.css` is the shared token source. Map every semantic role used by Tailwind and shadcn, including popover background/foreground and focus roles. Components use those tokens instead of their own hex values. Theme changes apply at the root so portaled content follows the same palette.

Keep component-specific layout rules with their feature. Change shared control appearance through its variants, not repeated descendant overrides such as “all buttons inside ticket details.” Avoid appending a new stylesheet patch for every screen; reconcile the rule that owns the behavior. A control must not change its appearance merely because it moved into a portal.

Keep content state separate from presentation. A collapsed group, resized pane, open menu, or expanded document cannot destroy a draft or reset a pending write. Retain core validation and retry semantics; visual feedback describes the actual result rather than predicting success.

When implementing a new token or recipe, update its shared definition and all affected usages together. The design specification remains the target; code must not silently redefine the target through local exceptions.

#### Chat motion

Chat uses the Refined language of section 12 with its tokens and primitives only. History never animates: what a Chat opens with, what catching up replays and a fold reopening are still. Reduced motion and the input guard make every item below instant.

- **Jump to latest.** Its strip keeps its 40px between the transcript and the tray, so it never covers text. The button fades up from a soft blur when the reader scrolls away and out in `--dur-exit` on return.
- **A Chat that needs you.** In the list the row's status dot arrives first (`--dur-enter`), then its word crossfades (held back `--dur-1`); the row then glides up into "Needs you" on the travel spring and its arrival fill follows.
